## Purpose and current scope

OpenFit is an independent Android watch-companion starter (`com.openfit.app`), not affiliated with Noise/NoiseFit. It has a local-only dashboard, BLE discovery for recognizable Noise/ColorFit names, saved-watch reconnect, a connect-first BLE flow with Android system bonding as an on-demand fallback (the supplied NoiseFit APK performs bond-check/createBond before connecting), QR scanning for QR contents that contain a Bluetooth MAC address, standard Bluetooth SIG heart-rate support, and manual local sleep-duration notes. On a Berry watch it now negotiates MTU and runs the vendor account bind over the GATT link (protocol → token → bind → confirm). That write path is implemented but **not yet confirmed by a physical watch**; the remaining health/notification commands are not wired yet. The recovered Berry profile (`PROTOCOL.md`) needs no application-level authentication, so the earlier "proprietary handshake blocks pairing" assumption no longer applies to that stack. There is no account, analytics, network permission, or cloud sync.

## Implementation notes

- Native Android app is implemented in Java in `app/src/main/java/com/openfit/app/MainActivity.java`.
- Min SDK 26, compile/target SDK 35. AGP 8.6.1 and Gradle 8.9; Java source compatibility 11; CI uses JDK 17.
- Pairing QR uses JourneyApps ZXing Embedded 4.3.0. CAMERA is requested at runtime. The app explicitly registers `com.journeyapps.barcodescanner.CaptureActivity` and overrides only its forced orientation lock (`tools:replace="android:screenOrientation"`); the library's own `zxing_CaptureTheme` is kept. QR contents are accepted only when they include a Bluetooth MAC address. **QR crash status 2026-11-17:** the reported tap-to-QR crash is consistent with ZXing 4.3.0's published POM omitting `androidx.core` and `androidx.fragment` while its bytecode uses `ContextCompat`, `ActivityCompat`, `Fragment`, `FragmentActivity` and `ActivityResultContract`; `launchQrScanner` also catches `LinkageError`. The dependency-fix commit `1bb2036` never produced an APK because CI failed at `:app:checkDebugDuplicateClasses` (`kotlin-stdlib-jdk8` 1.6.21 vs `kotlin-stdlib` 1.8.22). The shim modules are now excluded in `app/build.gradle`, so the fix can ship; the QR path still needs a physical retest. An uncaught-exception handler (`OpenFitApp`) now stores the last stack trace and the diagnostics report shows it, so any remaining crash is reportable without adb.
- Dashboard styling is intentionally dark and high contrast, with white/black surfaces, small red status accents, monospaced labels, and a live date. MainActivity now has bottom tabs for Home, Health, Devices, and Sleep; tab content is separated into panels.
- Heart-rate data is accepted only from the standard BLE Heart Rate Measurement characteristic (service 0x180D, characteristic 0x2A37). Daily min/max and minute sample counts are stored locally; they describe received notifications, not continuous monitoring.
- Manual sleep duration is stored locally and is not a device measurement or sleep-stage estimate.
- BLE screen has a selectable GATT diagnostics report listing discovered service/characteristic UUIDs and READ/WRITE/NOTIFY/INDICATE properties. It does not read/write proprietary characteristics. Previous hard-coded NoiseFit protobuf/base UUID guesses were removed; absence of SIG heart-rate support is no longer mislabeled as a protobuf-service result.
- BLE scan-start runtime exceptions now become visible status messages, and scan timeouts are canceled on stop/restart to avoid stale callbacks. QR result parsing is guarded and surfaces a retry/fallback message. These defensive changes are not confirmed fixes for the reported physical-device crash.
- Connect is now **connect-first**: the app starts `connectGatt` immediately, retries transient failures up to four times, treats `STATE_CONNECTED` with a non-success status as a failure, and only starts Android `createBond()` when the watch reports GATT insufficient-authentication/encryption (5/15) or service discovery/notification setup hits those statuses. Bonding has a 45 s timeout and reconnects through `ACTION_BOND_STATE_CHANGED` on success. This keeps the supplied NoiseFit APK's bonding path (`BerryBluetoothService` bond-check, `createBond`, bond-state receiver) as a fallback without letting a failed or hanging system pairing prompt block a watch that accepts a plain BLE link. After service discovery the app detects the Berry service (or SIG HRS / Ryeex) and enables available notifications sequentially with a timeout. On the Berry profile it then requests MTU 247 (23 fallback), chunks writes to `MTU - 3`, sends the vendor bind sequence (protocol cmd 1 → account token cmd 2 → bind cmd 3 if unbound → confirm cmd 4), reassembles split notifications, acks watch frames, and persists the account token per watch address. A bounded on-device log, a `BERRY PAIRING LOG` with TX/RX hex, and a Copy button in the diagnostics dialog capture the exact status codes for reporting. Verified on a physical ColorFit Ultra Buzz on Android 16: it connected while Android still reported it as not bonded, exposed six services including Berry `16186f00-…`, and accepted notification setup on all five Berry characteristics. The proprietary bind write path is untested on hardware.

A 2026-11-17 pass with a rootless JADX CLI install recovered the Berry profile end to end: GATT service `16186f00-0000-1000-8000-00807f9b34fb` (chars `…6f01`–`…6f05`, writes on `…6f02`), the 9-byte frame header, an 8-byte ack frame, the `SEWear` protobuf envelope, and the bind commands (protocol cmd 1, user id cmd 2, bind cmd 3, confirm cmd 4, with `UserIdBean`/`BerryDeviceInfoBean` layouts).
