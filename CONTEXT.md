## Purpose and current scope

OpenFit is an independent Android watch-companion starter (`com.openfit.app`), not affiliated with Noise/NoiseFit. It has a local-only dashboard, BLE discovery for recognizable Noise/ColorFit names, saved-watch reconnect, a connect-first BLE flow with Android system bonding as an on-demand fallback (the supplied NoiseFit APK performs bond-check/createBond before connecting), QR scanning for QR contents that contain a Bluetooth MAC address, standard Bluetooth SIG heart-rate support, and manual local sleep-duration notes. On a Noise watch exposing `16186f00` it negotiates MTU, probes the SE ("Apricot") chunked-protobuf transport, and binds through the vendor's ZhBracelet ("NavPlus") channel on `00000001` (`00000002` write / `00000003` notify). That key-108 bind is **confirmed on a physical ColorFit Ultra Buzz** (2026-11-18, `result=1`, watch left pairing mode) and persists across reconnects (`type=1 result=1`); the SE account group answers `NOT_SUPPORT` on this model and Berry-over-BLE is silent. After a successful bind the app now sends the vendor's clock sync (key 1) and, 50 ms later, the user-info profile (key 4). A second model, the **Noise Watch Beat**, has no `00000001` service but does implement the SE account group: it answers id 16 (`bound=false`) and id 17 (`bind_check_result=SUCCESS`, `device_verify=false`, name/MAC/firmware), so the app now continues to the id-18 `bind_result` instead of aborting on the flag. That path is implemented and unit-tested; the on-device confirmation is still pending. Remaining health/notification commands are not wired yet. There is no account, analytics, network permission, or cloud sync.

## Implementation notes

- Native Android app is implemented in Java in `app/src/main/java/com/openfit/app/MainActivity.java`.
- Min SDK 26, compile/target SDK 35. AGP 8.6.1 and Gradle 8.9; Java source compatibility 11; CI uses JDK 17.
- Pairing QR uses JourneyApps ZXing Embedded 4.3.0. CAMERA is requested at runtime. The app explicitly registers `com.journeyapps.barcodescanner.CaptureActivity` and overrides only its forced orientation lock (`tools:replace="android:screenOrientation"`); the library's own `zxing_CaptureTheme` is kept. QR contents are accepted only when they include a Bluetooth MAC address. **QR crash status 2026-11-17:** the reported tap-to-QR crash is consistent with ZXing 4.3.0's published POM omitting `androidx.core` and `androidx.fragment` while its bytecode uses `ContextCompat`, `ActivityCompat`, `Fragment`, `FragmentActivity` and `ActivityResultContract`; `launchQrScanner` also catches `LinkageError`. The dependency-fix commit `1bb2036` never produced an APK because CI failed at `:app:checkDebugDuplicateClasses` (`kotlin-stdlib-jdk8` 1.6.21 vs `kotlin-stdlib` 1.8.22). The shim modules are now excluded in `app/build.gradle`, so the fix can ship; the QR path still needs a physical retest. An uncaught-exception handler (`OpenFitApp`) now stores the last stack trace and the diagnostics report shows it, so any remaining crash is reportable without adb.
- Dashboard styling is intentionally dark and high contrast, with white/black surfaces, small red status accents, monospaced labels, and a live date. MainActivity now has bottom tabs for Home, Health, Devices, Sleep and Settings; tab content is separated into panels.
- **UI stack (2026-11-27):** the app is still Java with programmatic Views, but Home, Health, Sleep and Settings are Compose, sharing `Components.kt` for the monospaced eyebrow and the secondary button. Health has the heading, heart card, LOW/HIGH/SAMPLES stat tiles, read-only watch-history cards (steps, activity, sleep, SpO2, stress, wrist temperature, blood pressure) and an "about this data" card; Settings has the watch card, display/health/power toggles, sedentary window editor, alarm list and Forget watch. Devices keeps its Views UI because it hosts the interactive BLE lists. Kotlin 2.2.21 and Compose BOM 2025.10.01 (material3 1.4.0) are pinned because material3 1.5.x requires compileSdk 37 and AGP 9.1 while this project builds with compileSdk 35 / AGP 8.6.1. In 1.4.0 `MaterialExpressiveTheme`, `MotionScheme` and the expressive components are still `internal`; they only became public in 1.5.0, which needs a preview compileSdk (no stable `platforms;android-37` is published). The theme therefore uses the public `MaterialTheme` with oversized corner radii, emphasized display/title styles, and spring animation specs. `HealthScreenController` in `app/src/main/kotlin/com/openfit/app/ui` hosts one `ComposeView`; Java passes a `HealthUiState` on every update, so all BLE state stays in `MainActivity`. The design rule is: keep the Nothing-style monochrome/red/monospace language, and use the newest available Material 3 components; fall back to older M3 components when an expressive one is unavailable. `MainActivity.applySystemBarInsets()` pads the scroll area and bottom bar because targetSdk 35 enforces edge-to-edge.
- Heart-rate data is accepted from the standard BLE Heart Rate Measurement characteristic (service 0x180D, characteristic 0x2A37) when a watch exposes it, and from the ZhBracelet daily history frame (key `0x0D`) on watches bound through `00000001`. Daily min/max and minute sample counts are stored locally; the Zh value is the watch's own five-minute history, not continuous monitoring. The Buzz refuses the vendor's one-shot measurement command, so live `0x0B` reporting is not yet available.
- Manual sleep duration is stored locally and is not a device measurement or sleep-stage estimate.
- BLE screen has a selectable GATT diagnostics report listing discovered service/characteristic UUIDs and READ/WRITE/NOTIFY/INDICATE properties. It does not read/write proprietary characteristics. Previous hard-coded NoiseFit protobuf/base UUID guesses were removed; absence of SIG heart-rate support is no longer mislabeled as a protobuf-service result.
- BLE scan-start runtime exceptions now become visible status messages, and scan timeouts are canceled on stop/restart to avoid stale callbacks. QR result parsing is guarded and surfaces a retry/fallback message. These defensive changes are not confirmed fixes for the reported physical-device crash.
- Connect is now **connect-first**: the app starts `connectGatt` immediately, retries transient failures up to four times, treats `STATE_CONNECTED` with a non-success status as a failure, and only starts Android `createBond()` when the watch reports GATT insufficient-authentication/encryption (5/15) or service discovery/notification setup hits those statuses. Bonding has a 45 s timeout and reconnects through `ACTION_BOND_STATE_CHANGED` on success. This keeps the supplied NoiseFit APK's bonding path (`BerryBluetoothService` bond-check, `createBond`, bond-state receiver) as a fallback without letting a failed or hanging system pairing prompt block a watch that accepts a plain BLE link. After service discovery the app detects the Noise service (or SIG HRS / Ryeex) and enables available notifications sequentially with a timeout. On the Noise profile it then requests MTU 247 (23 fallback), announces and chunks SE commands (`MTU - 5` data bytes per chunk), answers the watch's inbound announces, reassembles the replies, and runs the vendor account bind (id 16 binding status → id 17 bind check → id 18 bind result, or id 19 token verification when already bound; the id-0 MTU greeting is skipped because this watch rejects it), persisting the account token per watch address. A bounded on-device log, a `PAIRING LOG` with TX/RX hex, and a Copy button in the diagnostics dialog capture the exact status codes for reporting. Verified on a physical ColorFit Ultra Buzz on Android 16: it connected while Android still reported it as not bonded, exposed six services including `16186f00-…`, and accepted notification setup on all five characteristics. A Berry-frame write attempt was answered with the SE busy control frame `00 00 01 02 00 00`, identifying the SE transport. On 2026-11-18 the watch answered the account probes with `SEWear{id=16, error_code=NOT_SUPPORT}` and the same for id 17, proving both the BLE envelope and the id numbering while showing that the vendor account bind is not on the SE channel for this model. A second run on the same date bonded the watch (`10 -> 11 -> 12`) but the classic SPP socket failed with `IOException · read failed, socket might closed or timeout, read ret: -1`, the signature of a remote with no RFCOMM listener. Berry has a second bearer for this case: `DEVICE_PROTOCOL_BERRY_TEST`/`BERRY_RING` are served by `BerryRingService`, a GATT client that writes the same `CmdDataBean` frames to `aa02` (Berry-Test, replies on `aa03`/`aa05`) or `0000005f` (Berry-Ring). A third run on 2026-11-18 showed the notification setup is now reliable (all SE CCCDs plus `aa03` inside the budget) and the watch answered the SE exchange frame by frame, but still with `NOT_SUPPORT` for ids 16/0/17; BLE Berry on `aa02` stayed silent. The decisive evidence is in the vendor APK: `NavPlusConnectHandler` binds ColorFit Ultra Buzz, Vision Buzz and Ultra 2 through the bundled `com.zjw.zhbraceletsdk`, a plaintext `0xAB` script protocol on service `00000001` (write `00000002`, notify `00000003`) whose key-108 bind request is answered by key 52 with a type/result byte. OpenFit therefore subscribes to `00000003` and tries the ZhBracelet bind (type 0, then a type-1 inquiry) before the `aa01` BLE Berry channel (private cmd 2/3/4 with the persisted token, then an `SEWear{type=ACCOUNT}` account query if the private command is silent). The classic bond + SPP path has been deleted: the watch is LE-only and exposes no SDP/SPP record. Two Berry bugs were fixed in the same change: the phone→watch head magic is `66 66 48 5A` (`BERRY_APP_REQ_DEV_HEAD_VALUE`) and the watch→phone one is `88 88 48 5A`, which OpenFit had swapped, and every inbound Berry frame is now acknowledged with the vendor's bare 8-byte ack because the exchange is stop-and-wait. The Berry phase also logs `BluetoothDevice.getType()` and the cached SDP UUIDs, which settle whether RFCOMM is possible at all. A connection-setup flag now covers the whole handshake (GATT connect, discovery, notification setup, bonding), so repeated Reconnect taps are ignored instead of opening a new GATT client each time; the Reconnect button stays hidden until the link is ready.
- **ZhBracelet settings (2026-11-27):** a full pass over `com.zjw.zhbraceletsdk` recovered every outgoing key, every incoming key, the `0x7F` private selectors, the `0x42` ack shape and the packed sedentary/alarm/device-info layouts. `ZhBraceletBinding` now builds and parses all of them, and the new Settings tab exposes clock sync, find watch, continuous HR, sedentary reminder, alarms and battery saver. Do-not-disturb (`0x20`) and bright screen (`0x0A`) are built and tested but deliberately not shown: the Buzz acknowledges or ignores those frames without a visible effect, so the rows were removed from the tab and only the protocol builders remain. Each write is optimistic and serialised with a 5 s watchdog; a refusal or silence reverts the control. Device info is requested on connect, while the stored sedentary/alarm values are read only on an explicit refresh so the post-bind burst is never raced. The exact map is in `PROTOCOL.md`; each command still needs an individual hardware check on the Buzz.
- **ZhBracelet heart rate (2026-11-19):** the watch pushes a 292-byte key `0x0D` frame after every successful bind. Bytes 13-14 carry a packed date and bytes 17-304 hold 288 five-minute samples; OpenFit decodes the date, latest nonzero sample, daily min/max/average and shows the latest value. On the Buzz the vendor's one-shot measurement (key `0x19`) is refused, while the continuous setting (key `0x29`) is acknowledged but does not produce a live `0x0B` frame in the log window. Cross-dex tracing of the full NoiseFit APK shows the vendor does use this SDK — `ZhBraceletService.setContinuousHr` is called from `NavPlusUpdateDeviceUnitsHandler.D0` — but never calls `openMeasurement`, so continuous HR is the only live measurement the vendor requests. The protobuf `SET_HEART_RATE_MONITOR` path writes to SE `16186f02`, which this firmware does not implement. The app delays `0x19` by 4 s so it no longer races the post-bind burst.
- **Read-only sensor history (2026-11-27):** the post-bind burst also carries steps/activity (`0x02`, `0x37`), sleep (`0x03`), SpO2 (`0x27`), stress (`0x38`), body temperature (`0x28`) and offline blood pressure (`0x10`). `ZhBraceletBinding` now parses all seven with bounds-checked counts and shared packed-date/record-time helpers, and the Health tab shows the latest value for each as a watch-history card. Nothing is requested from the watch, so these parsers cannot change its state. Keys `0x02`/`0x03` collide with outgoing alarm/step-target writes, so every parser requires the watch direction byte. Sleep totals follow the vendor (deep + light, REM separate); the sleep date is the packed date plus one day. Wrist temperature is shown as the raw byte because the vendor stores it unscaled and no public scale exists. Layouts and provenance are in `PROTOCOL.md`.

## NoiseFit protocol research and safety boundary

The user supplied `/home/shiv/com.noisefit_5.5.0.xapk` (NoiseFit 5.5.0, 313 MB), containing `com.noisefit.apk` (18 DEX files) plus ARM64, English, and density splits. A 2026-11-17 pass with a rootless JADX CLI install recovered the Berry profile end to end: GATT service `16186f00-0000-1000-8000-00807f9b34fb` (chars `…6f01`–`…6f05`, writes on `…6f02`), the 9-byte frame header, an 8-byte ack frame, the `SEWear` protobuf envelope, and the bind commands (protocol cmd 1, user id cmd 2, bind cmd 3, confirm cmd 4, with `UserIdBean`/`BerryDeviceInfoBean` layouts). That stack has no encryption or challenge/response. A follow-up pass recovered the SE ("Apricot") chunked-protobuf transport that `16186f00` actually uses, plus the `SEFunctionId` account bind messages (`SEBindAccount`/`SEBindCheck`/`SEBindResult`). The vendor ships two `SEWear` schemas: the BLE one (`com.zh.ble.wear.protobuf`, `id=1`, `bind_account=3`, no type) and the classic-SPP one (`com.zh.ble.sa_wear.protobuf`, `type=1`, `id=2`, `bind_account=4`); OpenFit keeps them in separate codecs (`SeWear`/`BerrySewear`). `libble-crypto.so`'s RC4-variant cipher and its `mixA/mixB` permutations are decoded for the alternate Ryeex stack, whose opcodes and handshake remain unknown. Full tables, provenance and open questions are in `PROTOCOL.md`; independent implementations of the Berry frame/protobuf/bind layer and the SE transport/bind layer live in `app/src/main/java/com/openfit/app/protocol/` and are covered by unit tests. Do not copy proprietary binaries, and do not claim application-level interoperability without a device test. The SE bind writes are now implemented, so the first install of the pairing build should be treated as the validation step for that write path.
